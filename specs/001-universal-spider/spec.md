# Feature Specification: 通用多源采集插件 (Universal Spider)

**Feature Branch**: `001-universal-spider`
**Created**: 2026-05-13
**Status**: Draft
**Input**: User description: "按照前面的结果，帮我实现一版通用采集方案，并自动配置好当前所独有的网址"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从单个源站自动采集软件文章 (Priority: P1)

作为站点管理员，我想要配置一个源站地址，系统能够自动从该源站采集软件介绍文章（标题、内容、封面图、分类、下载链接），并自动创建到我的站点中，这样我不需要手动搬运每篇文章。

**Why this priority**: 这是整个功能的核心价值——自动采集替代手动搬运。没有这个能力，其他一切都没有意义。

**Independent Test**: 配置一个源站 URL，运行采集任务，验证文章被成功创建且字段完整（标题、内容、分类、下载链接、封面图）。

**Acceptance Scenarios**:

1. **Given** 管理员已配置源站地址为 `https://www.gndown.com`，**When** 手动触发采集任务，**Then** 系统从该站采集所有未采集过的文章，并在本地创建对应文章记录
2. **Given** 系统已采集过某篇文章，**When** 再次运行采集任务，**Then** 该文章被跳过，不会重复创建
3. **Given** 源站返回 VIP 或置顶文章，**When** 采集任务运行，**Then** 这些文章被自动跳过

---

### User Story 2 - 通过配置文件管理多个源站 (Priority: P2)

作为站点管理员，我想要通过配置化的方式管理多个采集源站，每个源站有独立的选择器映射规则，这样我不需要为每个新源站写代码，只需要填写配置即可。

**Why this priority**: 扩展性是核心诉求。用户明确说"通用采集方案"，多源配置能力是区别于现有单站插件的关键。

**Independent Test**: 添加一个新的源站配置（不写代码），运行采集任务，验证能从新源站成功采集文章。

**Acceptance Scenarios**:

1. **Given** 管理员已配置两个源站（gndown.com 和 ludown.com），**When** 运行采集任务，**Then** 系统依次从两个源站采集文章
2. **Given** 管理员修改了某源站的选择器配置，**When** 保存配置后重新运行采集，**Then** 系统使用新选择器规则进行采集
3. **Given** 某源站不可访问，**When** 采集任务运行，**Then** 系统记录错误并继续采集其他源站，不会中断整个任务

---

### User Story 3 - 自动映射源站分类到本地分类 (Priority: P3)

作为站点管理员，我想要源站的分类能自动映射到本地站点的分类体系中，这样采集来的文章会自动归到正确的分类，不需要我手动调整。

**Why this priority**: 提升采集质量，减少人工干预。有了分类映射，采集来的文章才能直接上线。

**Independent Test**: 配置分类映射规则，采集一篇文章，验证其被归入正确的本地分类。

**Acceptance Scenarios**:

1. **Given** 源站分类"应用软件"已映射到本地分类 ID 5，**When** 采集到一篇"应用软件"分类的文章，**Then** 该文章的 CategoryID 自动设为 5
2. **Given** 源站某个分类未配置映射，**When** 采集到该分类的文章，**Then** 文章使用默认分类（如"其他软件"）
3. **Given** 管理员新增一条分类映射规则，**When** 保存后再次采集，**Then** 新规则立即生效

---

### User Story 4 - 下载链接智能提取与存储 (Priority: P4)

作为站点管理员，我想要采集插件能智能识别文章中的下载链接（百度云、夸克云、蓝奏云等），提取网盘类型、链接地址和访问密码，结构化存储到文章的扩展字段中。

**Why this priority**: 下载链接是软件站的核心数据，结构化存储后前端可以灵活展示。

**Independent Test**: 采集一篇文章，验证其下载链接被正确提取（类型、URL、密码），并存储在文章的 res/extends 字段中。

**Acceptance Scenarios**:

1. **Given** 文章包含"下载地址"区域及多个网盘链接，**When** 系统解析该文章，**Then** 提取所有下载链接，包含网盘类型（如"夸克云"、"百度云"）、URL 和密码
2. **Given** 文章不包含下载地址区域，**When** 系统解析该文章，**Then** 下载链接为空，文章内容保持完整
3. **Given** 某网盘链接后标注了"访问密码: abc123"，**When** 系统解析该链接，**Then** 密码 "abc123" 被一并提取

---

### Edge Cases

- 源站页面结构变化导致选择器失效时，系统能记录具体错误并跳过该篇文章，不影响其他文章采集
- 文章标题完全相同但来自不同源站时，通过源站标识+标题哈希生成唯一 slug，避免冲突
- 源站响应超时或返回非 200 状态码时，按配置重试次数自动重试
- 文章内容中包含相对路径图片时，自动转换为绝对路径
- 源站启用了反爬机制时，支持配置代理和请求间隔

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须支持通过插件 JSON 配置字段定义多个采集源站（JSON 数组格式），每个源站包含：基础 URL、CSS 选择器映射、请求参数（超时、重试、间隔、代理）、启用状态
- **FR-002**: 系统必须支持以下选择器配置项：文章列表选择器、文章链接选择器、标题选择器、正文内容选择器、分类选择器、封面图选择器、时间选择器、VIP/置顶标记选择器、下载地址标记选择器
- **FR-003**: 系统必须支持分类名称映射配置，将源站分类名称映射到本地分类 ID
- **FR-004**: 系统必须支持翻页采集，从第 1 页开始直到遇到整页已采集过的文章后停止
- **FR-005**: 系统必须通过 slug（源站标识 + 标题哈希）实现文章去重，避免重复采集
- **FR-006**: 系统必须支持下载链接的结构化提取，包括网盘类型、URL 和访问密码
- **FR-007**: 系统必须支持请求限速，可配置请求间隔（秒），避免对源站造成过大压力
- **FR-008**: 系统必须支持代理配置，通过代理发送请求以应对源站的反爬策略
- **FR-009**: 系统必须支持定时任务（Cron），按配置的间隔自动执行采集
- **FR-010**: 系统必须支持手动触发单次采集任务
- **FR-011**: 系统必须将采集过程中的错误（网络失败、解析失败、创建失败）记录到日志中，不中断整体采集流程
- **FR-012**: 系统必须支持图片路径自动转换（相对路径 → 绝对路径，协议相对路径 → https）
- **FR-013**: 系统必须支持 VIP/置顶文章的自动跳过，通过配置选择器识别
- **FR-014**: 系统必须为每个源站预设默认的选择器配置，管理员只需填写 URL 即可开始采集
- **FR-015**: 系统必须与现有 GnDownSpider 插件并存运行，使用独立的插件 ID，但数据格式（slug、extends、res 字段结构）保持兼容，避免与旧插件采集的数据冲突

### Key Entities

- **SpiderSiteConfig（采集源站配置）**: 包含源站 ID、名称、基础 URL、选择器映射、分类映射表、请求参数（超时/重试/间隔/代理）、启用状态
- **SelectorMapping（选择器映射）**: 定义如何从 HTML 页面中提取各类数据（标题、内容、分类、封面图等），每项包含选择器字符串和属性名
- **CategoryMapping（分类映射）**: 源站分类名称到本地分类 ID 的对应关系
- **SpiderResult（采集结果）**: 单次采集任务的统计信息（采集数量、跳过数量、错误数量、耗时）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员添加一个新源站时，如果该源站已预设选择器配置，5 分钟内（含运行首次采集）即可看到采集到的文章
- **SC-002**: 采集到的文章字段完整率 ≥ 95%（标题、内容、分类三个核心字段均不为空）
- **SC-003**: 系统支持同时管理 ≥ 5 个源站，且能稳定运行不出现内存泄漏或崩溃
- **SC-004**: 重复运行采集任务时，已采集的文章 100% 被正确跳过，不产生重复记录
- **SC-005**: 单篇文章采集耗时（含网络请求 + 解析）≤ 5 秒（正常网络条件下）
- **SC-006**: 源站不可达时，系统在 30 秒内记录错误并继续处理下一个源站

## Clarifications

### Session 2026-05-13

- Q: 采集源站配置的存储方式？ → A: 插件 JSON 字段：将所有源站配置作为 JSON 数组存储在插件的配置字段中（与现有 GnDownSpider 方式一致，通过 moss 插件配置界面管理）
- Q: 采集文章中的图片如何处理？ → A: 保留源站原始图片 URL，不做本地下载（与现有 GnDownSpider 行为一致，已有 SaveArticleImages 插件可按需下载）
- Q: 新插件与现有 GnDownSpider 的关系？ → A: 并存运行：新建通用插件与 GnDownSpider 同时存在，管理员自行选择使用哪个
- Q: 多源站的采集执行方式？ → A: 顺序执行：按配置顺序逐个源站采集，完成一个再采集下一个
- Q: 采集的文章内容后处理范围？ → A: 仅做基本清理：移除下载地址区域、转换图片路径为绝对路径、提取下载链接，其余内容原样保留（与现有 GnDownSpider 行为一致）

## Assumptions

- 源站均为中文软件下载站，页面结构以 HTML 为主（非 SPA），可通过 HTTP GET 直接获取内容
- 大部分源站使用 WordPress 或类似的 CMS 系统，HTML 结构有规律可循
- 已有 GnDownSpider 插件作为参考实现，新插件在数据模型层面（Article entity 的 Slug、Extends、Res 字段）与之保持兼容
- 本地站点的分类体系（应用软件、系统工具、编程开发等）已创建好，分类映射基于名称匹配
- 源站的下载链接通常以 `<h5>下载地址</h5>` 或类似标记作为分隔符，后面跟着网盘链接列表
- 管理员具有基本的 CSS 选择器知识，或使用预设配置即可
- 插件运行环境与现有 moss 系统一致（Go 后端、GORM、现有 request 工具库）
